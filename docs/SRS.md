# Техническое задания

> Функциональные и нефункциональные требования к разрабатываемому ПО по части структуры спецификации "Software Requirements Specification".

## Термины и определения

| Термин | Определение |
| --- | --- |
| BotNetHunter | Веб-приложение для анализа профилей и сообществ ВКонтакте на признаки ботоподобного поведения. |
| Пользователь | Зарегистрированный участник системы, выполняющий анализ VK-профилей и VK-сообществ и просматривающий собственную историю проверок. |
| Администратор | Привилегированная учетная запись, управляющая пользователями, VK API токенами, параметрами анализа и системными метриками. |
| VK API | Внешний HTTP API социальной сети ВКонтакте, используемый системой для получения данных профилей, групп, публикаций, комментариев и реакций. |
| Цель анализа | Профиль пользователя ВКонтакте или сообщество ВКонтакте, заданные ID, коротким именем или ссылкой. |
| Балл риска | Числовая оценка от 0 до 100, показывающая вероятность ботоподобного поведения. Чем выше значение, тем выше риск. |
| Уровень риска | Категория результата анализа: `NORMAL`, `LOW`, `MEDIUM` или `HIGH` в зависимости от итогового балла и типа анализа. |
| История анализа | Сохраненная запись о выполненной проверке, включающая цель, тип цели, статус, дату, балл риска и детализацию факторов. |
| VK API токен | Токен доступа к VK API, добавляемый администратором и используемый системой при обращении к внешнему сервису. |
| 2FA | Двухфакторная аутентификация на основе TOTP-кодов из приложения-аутентификатора. |
| CSRF | Межсайтовая подделка запроса; класс атак, от которого HTML-формы защищаются CSRF-токенами. |
| Rate limiting | Ограничение частоты запросов к системе по IP-адресу или Bearer-токену. |

## 1 Функциональные требования

> Уточненный (по группам функциональных требований к проекту) перечень функций, выполняемых системой.

### Требования к управлению пользователями

#### Функциональное требование 1. Регистрация пользователя

Описание: система должна позволять новому пользователю создать учетную запись по email и паролю.

Триггер запуска функции: пользователь отправляет форму регистрации на странице `/register`.

Входные данные: email, пароль длиной не менее 8 символов.

Результат: создается запись пользователя с активным статусом, хэшированным паролем, дневным лимитом запросов по умолчанию и начальной статистикой использования.

Критерии приемки:
- система не должна создавать двух пользователей с одинаковым email;
- пароль должен храниться только в виде криптографического хэша;
- при успешной регистрации пользователь получает активную сессию или перенаправляется к входу согласно текущей реализации интерфейса;
- при ошибке валидации пользователь получает понятное сообщение.

#### Функциональное требование 2. Просмотр личного кабинета

Описание: система должна предоставлять пользователю личный кабинет с формой запуска анализа, остатком дневного лимита, статусом текущего анализа и последними записями истории.

Триггер запуска функции: авторизованный пользователь открывает `/dashboard`.

Входные данные: сессионная cookie пользователя.

Результат: отображается dashboard пользователя.

Критерии приемки:
- неавторизованный пользователь перенаправляется на страницу входа;
- история должна отображаться в обратном хронологическом порядке;
- отображаемый остаток лимита должен учитывать `requests_today` и `requests_limit`.

#### Функциональное требование 3. Смена пароля

Описание: система должна позволять авторизованному пользователю изменить пароль.

Триггер запуска функции: пользователь отправляет форму `/account/change-password`.

Входные данные: текущий пароль, новый пароль, повтор нового пароля, CSRF-токен.

Результат: пароль пользователя заменяется новым хэшем.

Критерии приемки:
- запрос без авторизации отклоняется;
- текущий пароль должен быть проверен перед изменением;
- новый пароль и повтор должны совпадать;
- новый пароль должен соответствовать минимальной длине;
- после успешной смены пользователь получает сообщение об успехе.

#### Функциональное требование 4. Удаление аккаунта

Описание: система должна позволять пользователю удалить собственный аккаунт.

Триггер запуска функции: пользователь отправляет запрос `/account/delete`.

Входные данные: сессионная cookie пользователя.

Результат: учетная запись пользователя и связанные с ней данные удаляются или становятся недоступными, пользовательская сессия завершается.

Критерии приемки:
- пользователь не может удалить чужой аккаунт;
- после удаления cookie сессии должна быть удалена;
- повторный вход под удаленной учетной записью невозможен.

#### Функциональное требование 5. Управление пользователями администратором

Описание: система должна предоставлять администратору список пользователей и операции блокировки, разблокировки и изменения дневного лимита запросов.

Триггер запуска функции: администратор открывает `/admin/users` или отправляет действие управления пользователем.

Входные данные: идентификатор пользователя, новое значение лимита при изменении лимита.

Результат: состояние пользователя обновляется.

Критерии приемки:
- доступ к функции имеет только администратор;
- при блокировке пользователя все его активные сессии должны быть деактивированы;
- лимит пользователя должен сохраняться в допустимых границах от 1 до 10000;
- администратор не должен случайно заблокировать встроенную административную учетную запись.

#### Функциональное требование 6. Управление пользовательскими сессиями

Описание: система должна позволять администратору просматривать активные сессии и деактивировать отдельную сессию или все сессии выбранного пользователя.

Триггер запуска функции: администратор открывает `/admin/sessions` или отправляет POST-запрос деактивации сессии.

Входные данные: идентификатор сессии или пользователя.

Результат: выбранные сессии переводятся в неактивное состояние.

Критерии приемки:
- неактивная сессия не должна давать доступ к защищенным страницам;
- при деактивации сессии связанная cookie должна перестать приниматься системой;
- доступ к управлению сессиями должен быть закрыт для обычных пользователей.

### Требования к аутентификации и авторизации

#### Функциональное требование 7. Авторизация пользователя

Описание: система должна выполнять вход пользователя по email и паролю.

Триггер запуска функции: пользователь отправляет форму `/login`.

Входные данные: email, пароль, CSRF-токен.

Результат: при успешной проверке создается JWT-сессия и запись активной сессии.

Критерии приемки:
- заблокированный пользователь не должен получать доступ к системе;
- неверные учетные данные не должны раскрывать, какое поле введено ошибочно;
- cookie сессии должна иметь атрибуты `HttpOnly` и `SameSite=Lax`;
- срок действия основной сессии должен быть ограничен.

#### Функциональное требование 8. Авторизация администратора

Описание: система должна выполнять вход администратора по учетным данным из переменных окружения.

Триггер запуска функции: администратор отправляет форму `/login` с административными учетными данными.

Входные данные: `ADMIN_EMAIL`, `ADMIN_PASSWORD`, CSRF-токен.

Результат: создаются административные cookie, пользователь перенаправляется в панель `/admin`.

Критерии приемки:
- учетные данные администратора не должны храниться в базе данных как обычный пользовательский пароль;
- маршруты `/admin/*` должны проверять административную сессию;
- обычный пользователь не должен получать доступ к административной панели.

#### Функциональное требование 9. Двухфакторная аутентификация

Описание: система должна позволять пользователю включить и отключить 2FA на основе TOTP.

Триггер запуска функции: пользователь открывает `/account/2fa/setup`, подтверждает код через `/account/2fa/enable` или отключает 2FA через `/account/2fa/disable`.

Входные данные: временный TOTP-секрет, 6-значный OTP-код, CSRF-токен.

Результат: для учетной записи сохраняется или удаляется TOTP-секрет и флаг активности 2FA.

Критерии приемки:
- 2FA включается только после проверки корректного OTP-кода;
- при включенной 2FA вход после проверки пароля должен требовать второй шаг `/login/2fa`;
- временный токен второго шага должен иметь ограниченный срок действия;
- неверный OTP-код не должен открывать доступ к личному кабинету.

#### Функциональное требование 10. Разграничение доступа

Описание: система должна ограничивать доступ к данным и функциям в соответствии с ролью.

Триггер запуска функции: любой запрос к защищенному маршруту.

Входные данные: cookie сессии или Bearer-токен.

Результат: запрос выполняется только при наличии достаточных прав.

Критерии приемки:
- пользователь может просматривать только собственные записи истории;
- администратор может просматривать административные разделы и записи анализа;
- неавторизованные запросы к API должны получать `401`;
- запросы к несуществующим или чужим записям должны получать отказ без раскрытия лишних данных.

### Требования к функциям загрузки и обработки файлов

#### Функциональное требование 11. Загрузка аватара пользователя

Описание: система должна позволять авторизованному пользователю загрузить изображение аватара.

Триггер запуска функции: пользователь отправляет multipart-форму `/account/avatar/upload`.

Входные данные: файл изображения, CSRF-токен, опциональный `upload_id` для отслеживания прогресса.

Результат: файл сохраняется в хранилище аватаров, путь к нему записывается в профиль пользователя.

Критерии приемки:
- принимать разрешается только изображения JPG, PNG, GIF и WebP, определенные по содержимому файла;
- пустой файл должен отклоняться;
- файл больше `MAX_UPLOAD_SIZE_BYTES` должен отклоняться до сохранения;
- старый аватар должен удаляться после успешного сохранения нового;
- пользователь без авторизации не может загрузить файл.

#### Функциональное требование 12. Отслеживание прогресса загрузки

Описание: система должна сообщать клиенту прогресс обработки загружаемого аватара.

Триггер запуска функции: клиент подключается к WebSocket `/ws/uploads/{upload_id}` и выполняет загрузку файла с тем же `upload_id`.

Входные данные: `upload_id`, события обработки файла.

Результат: клиент получает статусы `processing`, `storing`, `done` или `error` с процентом выполнения.

Критерии приемки:
- прогресс должен обновляться во время чтения и сохранения файла;
- при ошибке загрузки клиент должен получить фазу `error`;
- завершенная загрузка должна отдавать фазу `done` и 100%.

#### Функциональное требование 13. Получение и публикация аватара

Описание: система должна предоставлять пользователю доступ к собственному аватару и возможность создать публичную ссылку на аватар.

Триггер запуска функции: пользователь открывает `/account/avatar/me` или отправляет `/account/avatar/share`; внешний клиент открывает `/shared/avatar/{token}`.

Входные данные: пользовательская сессия или публичный токен аватара.

Результат: возвращается изображение аватара либо публичная ссылка.

Критерии приемки:
- собственный аватар доступен только авторизованному владельцу;
- публичный аватар доступен только по валидному подписанному токену;
- при отсутствии файла система должна возвращать ошибку 404.

#### Функциональное требование 14. Запуск анализа профиля ВКонтакте

Описание: система должна анализировать профиль ВКонтакте на признаки ботоподобного поведения.

Триггер запуска функции: пользователь отправляет цель анализа с `target_type=user` через `/analyze` или `/api/analyze`.

Входные данные: ID, короткое имя или ссылка на VK-профиль.

Результат: создается запись истории с итоговым баллом риска, уровнем риска и перечнем факторов.

Критерии приемки:
- система должна нормализовать VK-ссылку до идентификатора цели;
- при отсутствии активных VK API токенов запрос должен завершаться ошибкой доступности сервиса;
- при недоступном или несуществующем профиле система должна возвращать ошибку анализа;
- успешный анализ должен увеличивать использованный дневной лимит пользователя на 1.

#### Функциональное требование 15. Запуск анализа сообщества ВКонтакте

Описание: система должна анализировать сообщество ВКонтакте по публикациям, комментариям, реакциям и профилям участников активности.

Триггер запуска функции: пользователь отправляет цель анализа с `target_type=group` через `/analyze` или `/api/analyze`.

Входные данные: ID, короткое имя или ссылка на VK-сообщество.

Результат: создается запись истории со средним баллом риска, уровнем риска, количеством обработанных публикаций, участников активности и сводкой нарушений.

Критерии приемки:
- система должна получать данные группы через VK API;
- закрытая группа или недоступная стена должны приводить к ошибке анализа;
- в деталях результата должны сохраняться причины и агрегированная сводка нарушений;
- использованный дневной лимит должен увеличиваться на количество учтенных единиц анализа.

#### Функциональное требование 16. Фоновая обработка анализа через Web UI

Описание: запуск анализа через HTML-интерфейс должен быстро создавать задачу и выполнять ее в фоне.

Триггер запуска функции: пользователь отправляет форму `/analyze`.

Входные данные: цель анализа, тип цели, CSRF-токен.

Результат: запись истории получает статус `pending`, затем `completed` или `failed`.

Критерии приемки:
- пользователь не должен иметь более одной активной `pending`-задачи одновременно;
- статус анализа должен быть доступен через `/analysis/status/{record_id}`;
- при успешном завершении статус должен стать `completed`;
- при ошибке анализа статус должен стать `failed`, а детали должны содержать сообщение об ошибке.

#### Функциональное требование 17. Просмотр истории и детального отчета

Описание: система должна сохранять и отображать историю анализов и детальные отчеты.

Триггер запуска функции: пользователь открывает `/dashboard`, `/history/{history_id}`, `/api/history` или `/api/history/{history_id}`.

Входные данные: идентификатор записи истории, параметры пагинации API.

Результат: пользователь получает список проверок или детальный отчет.

Критерии приемки:
- API истории должен поддерживать `limit` от 1 до 100 и `offset` от 0;
- детальный отчет должен включать цель, тип цели, баллы, уровень риска, дату и детализацию факторов;
- пользователь не должен видеть чужие записи;
- время отображения должно приводиться к московскому часовому поясу там, где это предусмотрено интерфейсом.

#### Функциональное требование 18. Публичная ссылка на отчет

Описание: система должна позволять создать публичную ссылку на результат анализа.

Триггер запуска функции: пользователь открывает отчет или отправляет `/history/{history_id}/share`.

Входные данные: идентификатор записи истории.

Результат: создается токен публичного отчета и ссылка `/public/report/{token}`.

Критерии приемки:
- публичная ссылка должна открывать только отчет, связанный с токеном;
- просроченная ссылка не должна открывать отчет;
- пользователь может создавать ссылку только на собственный отчет;
- токен ссылки должен быть криптографически случайным.

### Требования к администрированию аналитических параметров и токенов

#### Функциональное требование 19. Управление VK API токенами

Описание: система должна позволять администратору добавлять, отключать, включать и удалять VK API токены.

Триггер запуска функции: администратор использует раздел `/admin/tokens`.

Входные данные: значение токена, описание токена, идентификатор токена для операций изменения.

Результат: пул активных VK API токенов обновляется.

Критерии приемки:
- дубликаты токенов не должны сохраняться;
- отключенный токен не должен использоваться для новых запросов к VK API;
- после изменения токенов менеджер токенов должен использовать обновленное состояние;
- доступ к токенам должен иметь только администратор.

#### Функциональное требование 20. Настройка параметров анализа

Описание: система должна позволять администратору изменять веса, пороги и штрафы аналитических правил.

Триггер запуска функции: администратор сохраняет форму `/admin/settings/save`.

Входные данные: числовые значения параметров анализа и CSRF-токен.

Результат: параметры сохраняются в базе данных и используются последующими анализами.

Критерии приемки:
- некорректные числовые значения не должны нарушать работу системы;
- параметры должны иметь значения по умолчанию;
- изменение параметров должно быть доступно только администратору;
- параметры анализа должны сохраняться между перезапусками приложения.

#### Функциональное требование 21. Просмотр системных метрик

Описание: система должна предоставлять администратору сводку состояния системы.

Триггер запуска функции: администратор открывает `/admin` или `/admin/metrics`.

Входные данные: административная сессия.

Результат: отображаются показатели пользователей, запросов, активных токенов, загрузки CPU, памяти, диска и недавней активности.

Критерии приемки:
- метрики должны быть доступны только администратору;
- главная панель администратора должна показывать общее количество пользователей, запросов и активных токенов;
- страница метрик должна показывать данные за последние 24 часа, если они доступны.

## 2 Требования к интерфейсам

> Уточненный список требований к интерфейсам системы.

### Требования к графическому интерфейсу управления администратора системы

#### Требование к интерфейсу 1. Панель администратора

Описание: интерфейс администратора должен предоставлять навигацию по разделам обзора, пользователей, сессий, токенов, параметров анализа и метрик.

Критерии приемки:
- все административные страницы должны быть доступны только после административной авторизации;
- при отсутствии административной сессии пользователь должен перенаправляться на страницу входа;
- интерфейс должен отображать сообщения об успешных и ошибочных операциях.

#### Требование к интерфейсу 2. Управление пользователями

Описание: страница `/admin/users` должна отображать список пользователей и элементы управления статусом и лимитами.

Критерии приемки:
- для пользователя должны отображаться email, дата создания, активность и лимит запросов;
- администратор должен иметь доступные действия блокировки, разблокировки, изменения лимита и деактивации сессий;
- операции должны выполняться через POST-запросы.

#### Требование к интерфейсу 3. Управление VK API токенами

Описание: страница `/admin/tokens` должна отображать список токенов и форму добавления нового токена.

Критерии приемки:
- интерфейс должен показывать количество активных токенов;
- для каждого токена должны быть доступны включение/отключение и удаление;
- значение токена не должно демонстрироваться лишним пользователям.

#### Требование к интерфейсу 4. Настройка анализа

Описание: страница `/admin/settings` должна позволять изменять параметры анализа без изменения исходного кода.

Критерии приемки:
- параметры должны быть сгруппированы по смыслу: лимиты, пороги, штрафы профиля, штрафы активности и штрафы публикаций;
- сохранение должно быть защищено CSRF-токеном;
- после сохранения администратор должен получить подтверждение.

#### Требование к интерфейсу 5. Метрики и обзор

Описание: страницы `/admin` и `/admin/metrics` должны визуально представлять состояние системы и последнюю активность.

Критерии приемки:
- обзор должен содержать количество пользователей, новых пользователей за день, запросов за день, общее количество запросов и активные токены;
- метрики должны включать CPU, память, диск, ошибки API и активность запросов;
- таблица недавней активности должна показывать последние анализы.

### Требования внешним интерфейсам системы HTTP API

#### Требование к интерфейсу 6. REST API анализа

Описание: система должна предоставлять внешний HTTP API для запуска анализа.

Метод и путь: `POST /api/analyze`.

Формат входа: JSON-объект с полями `target` и `target_type`.

Формат выхода: JSON-объект `AnalyzeResponse` с полями `id`, `target`, `target_type`, `score`, `risk_level`, `average_score`, `members_analyzed`, `details`, `created_at`.

Критерии приемки:
- `target` должен быть непустой строкой длиной не более 255 символов;
- `target_type` должен принимать только значения `user` или `group`;
- успешное создание результата должно возвращать HTTP 201;
- неавторизованный запрос должен возвращать HTTP 401.

#### Требование к интерфейсу 7. REST API истории

Описание: система должна предоставлять API для получения истории анализов текущего пользователя.

Методы и пути:
- `GET /api/history`;
- `GET /api/history/{history_id}`.

Критерии приемки:
- список истории должен поддерживать пагинацию через `limit` и `offset`;
- детальный endpoint должен возвращать только запись текущего пользователя или доступную администратору запись;
- при отсутствии записи должен возвращаться HTTP 404.

#### Требование к интерфейсу 8. Служебные HTTP-интерфейсы

Описание: система должна предоставлять служебные endpoints для проверки состояния и версии.

Методы и пути:
- `GET /health`;
- `GET /api/version`;
- `GET /api-docs`;
- `GET /api-docs/openapi.yaml`.

Критерии приемки:
- `/health` должен возвращать статус `ok`, имя сервиса и версию;
- `/api/version` должен возвращать версию приложения, версию VK API и номер сборки;
- OpenAPI-спецификация должна быть доступна в формате YAML;
- Swagger UI должен открываться по `/api-docs`.

#### Требование к интерфейсу 9. Формат ошибок API

Описание: HTTP API должен возвращать ошибки в машинно-читаемом JSON-формате.

Критерии приемки:
- для ошибок авторизации должен использоваться HTTP 401;
- для превышения лимита должен использоваться HTTP 429 и заголовок `Retry-After`;
- для отсутствия активных VK API токенов должен использоваться HTTP 503;
- для ошибок входных данных или недоступной цели анализа должен использоваться HTTP 400.

#### Требование к интерфейсу 10. Авторизация API

Описание: API должен поддерживать авторизацию по Bearer-токену и совместимость с cookie-сессией Web UI.

Критерии приемки:
- валидный Bearer-токен должен определять текущего пользователя;
- валидная cookie Web UI должна приниматься для совместимых API-запросов;
- заблокированный пользователь не должен проходить авторизацию;
- административная cookie должна распознаваться как административный доступ там, где это предусмотрено.

### Требования к графическому интерфейсу пользователя системы

#### Требование к интерфейсу 11. Страницы входа и регистрации

Описание: пользовательский интерфейс должен предоставлять страницы входа, регистрации и второго фактора.

Критерии приемки:
- стартовая страница `/` должна отображать форму входа;
- `/register` должна отображать форму создания учетной записи;
- `/login/2fa` должна отображаться только при действительном временном токене второго шага;
- сообщения об ошибках должны быть понятны пользователю.

#### Требование к интерфейсу 12. Личный кабинет

Описание: `/dashboard` должен быть основным рабочим экраном пользователя.

Критерии приемки:
- интерфейс должен содержать форму ввода VK-ссылки, ID или username;
- пользователь должен выбирать тип цели: профиль или группа;
- интерфейс должен показывать прогресс или статус выполняющегося анализа;
- история последних проверок должна быть доступна без перехода в отдельный раздел.

#### Требование к интерфейсу 13. Детальный отчет

Описание: страница `/history/{history_id}` должна отображать результат анализа в понятном виде.

Критерии приемки:
- для профиля должны отображаться итоговый балл, уровень риска и факторы оценки;
- для группы должны отображаться средний балл, количество обработанных публикаций, количество участников активности и сводка нарушений;
- страница должна предоставлять публичную ссылку на отчет, если она доступна;
- недоступная пользователю запись не должна отображаться.

#### Требование к интерфейсу 14. Управление аккаунтом

Описание: пользовательский интерфейс должен предоставлять операции смены пароля, включения/отключения 2FA, загрузки аватара, публикации аватара и удаления аккаунта.

Критерии приемки:
- все операции изменения состояния должны выполняться с CSRF-защитой;
- интерфейс должен отображать текущий статус 2FA;
- загрузка аватара должна показывать результат операции и, при наличии клиента прогресса, статус загрузки;
- удаление аккаунта должно завершать пользовательскую сессию.

## 3 Нефункциональные требования

> Уточненный список нефункциональных требований системе.

### Требования к обработке больших данных

#### Нефункциональное требование 1. Ограничение объема анализа

Описание: система должна ограничивать объем данных, получаемых из VK API, настраиваемыми параметрами.

Критерии приемки:
- количество анализируемых публикаций группы должно определяться параметром `posts_limit`;
- количество комментариев должно ограничиваться параметром `comments_limit`;
- задержка между запросами к VK API должна задаваться `REQUEST_DELAY`;
- при превышении ограничений VK API система должна использовать повторные попытки и ожидание согласно настройкам клиента.

#### Нефункциональное требование 2. Фоновая обработка долгих операций

Описание: операции анализа, способные занимать больше времени, не должны блокировать отклик HTML-интерфейса.

Критерии приемки:
- Web UI должен создавать запись `pending` и возвращать управление пользователю;
- клиент должен иметь возможность опрашивать статус анализа;
- ошибки фоновой задачи должны сохраняться в истории как `failed`.

#### Нефункциональное требование 3. Дневные лимиты использования

Описание: система должна защищать VK API и инфраструктуру от чрезмерного использования через пользовательские дневные лимиты.

Критерии приемки:
- лимит должен сбрасываться при наступлении нового дня по московскому времени;
- при исчерпании лимита система должна возвращать HTTP 429;
- администратор должен иметь возможность менять лимит пользователя.

#### Нефункциональное требование 4. Ограничение размера загружаемых файлов

Описание: система должна предотвращать загрузку чрезмерно больших файлов.

Критерии приемки:
- максимальный размер должен задаваться переменной `MAX_UPLOAD_SIZE_BYTES`;
- проверка `Content-Length` должна выполняться до полного чтения тела запроса, если заголовок доступен;
- при превышении размера система должна возвращать HTTP 413.

### Требования к безопасности

#### Нефункциональное требование 5. Хранение секретов

Описание: секреты системы должны храниться во внешней конфигурации, а не в исходном коде.

Критерии приемки:
- `SECRET_KEY`, `DATABASE_URL`, `ADMIN_EMAIL` и `ADMIN_PASSWORD` должны задаваться через переменные окружения;
- приложение не должно запускаться без обязательных секретов;
- файл `.env` не должен попадать в репозиторий.

#### Нефункциональное требование 6. Защита паролей и сессий

Описание: учетные данные и сессии должны храниться безопасно.

Критерии приемки:
- пароли пользователей должны хэшироваться алгоритмом Argon2id или эквивалентным стойким алгоритмом;
- JWT-токены должны подписываться `SECRET_KEY`;
- в базе данных должен храниться хэш сессионного токена, а не исходный токен;
- cookie сессии должны быть `HttpOnly`, `SameSite=Lax`, а в production-конфигурации также `Secure`.

#### Нефункциональное требование 7. CSRF-защита

Описание: HTML-формы, изменяющие состояние системы, должны быть защищены от CSRF.

Критерии приемки:
- формы должны содержать CSRF-токен;
- сервер должен сравнивать токен в форме с токеном, вычисленным на основе cookie-секрета;
- запрос с отсутствующим или неверным CSRF-токеном должен отклоняться HTTP 403.

#### Нефункциональное требование 8. Защитные HTTP-заголовки и CORS

Описание: система должна устанавливать защитные HTTP-заголовки и ограничивать CORS.

Критерии приемки:
- ответы должны содержать `Content-Security-Policy`, `X-Content-Type-Options` и `X-Frame-Options`;
- CORS должен разрешать только явно заданные origin;
- wildcard `*` для production CORS не допускается;
- preflight-запросы с недоверенных origin должны отклоняться.

#### Нефункциональное требование 9. Ограничение частоты запросов

Описание: система должна ограничивать частоту HTTP-запросов по IP-адресу или Bearer-токену.

Критерии приемки:
- при превышении лимита система должна возвращать HTTP 429;
- ответ должен содержать `Retry-After` и заголовки с информацией о лимите;
- health-check и статические файлы могут быть исключены из ограничения.

#### Нефункциональное требование 10. Логирование и трассировка

Описание: система должна вести журналы запросов и ошибок с идентификатором запроса.

Критерии приемки:
- каждый HTTP-запрос должен получать `X-Request-ID`;
- при отсутствии входящего `X-Request-ID` система должна генерировать новый идентификатор;
- ошибки анализа и загрузки файлов должны записываться в журнал.

### Требования к инфраструктуре

#### Нефункциональное требование 11. Среда исполнения

Описание: система должна запускаться в поддерживаемой серверной среде.

Критерии приемки:
- основной язык исполнения: Python 3.11;
- веб-фреймворк: FastAPI;
- ASGI-сервер: Uvicorn;
- шаблонизация HTML: Jinja2;
- база данных: PostgreSQL через SQLAlchemy.

#### Нефункциональное требование 12. Контейнеризация

Описание: система должна поддерживать запуск в Docker Compose.

Критерии приемки:
- приложение и PostgreSQL должны запускаться в отдельных контейнерах;
- данные PostgreSQL должны храниться в Docker volume;
- внешний доступ к приложению должен осуществляться через опубликованный порт приложения или через nginx reverse proxy;
- конфигурация должна передаваться через переменные окружения.

#### Нефункциональное требование 13. База данных и хранение данных

Описание: система должна надежно хранить пользователей, сессии, историю анализа, параметры, токены и публичные ссылки.

Критерии приемки:
- схема должна включать сущности пользователей, сессий, истории анализа, настроек администратора, параметров модулей, VK-токенов и публичных отчетов;
- история пользователя должна удаляться каскадно при удалении пользователя;
- записи истории должны содержать статус выполнения и время создания;
- параметры анализа и VK-токены должны сохраняться между перезапусками.

#### Нефункциональное требование 14. Мониторинг

Описание: система должна предоставлять метрики для мониторинга приложения.

Критерии приемки:
- приложение должно публиковать Prometheus-метрики;
- администраторский интерфейс должен отображать CPU, память, диск, количество запросов и ошибки API;
- счетчик rate limit должен учитывать заблокированные запросы.

#### Нефункциональное требование 15. Документирование API и эксплуатации

Описание: система должна иметь документацию для пользователей, администраторов и внешних интеграций.

Критерии приемки:
- OpenAPI-спецификация должна храниться в `docs/api/swagger.yaml`;
- Swagger UI должен быть доступен по `/api-docs`;
- репозиторий должен содержать руководство пользователя, описание системы, безопасность, развертывание и CI/CD-документацию;
- версия приложения должна быть доступна через `/api/version` и отображаться в интерфейсе версии.

#### Нефункциональное требование 16. Надежность при отказах внешнего VK API

Описание: система должна корректно обрабатывать ошибки VK API и отсутствие токенов.

Критерии приемки:
- при отсутствии активных VK API токенов анализ должен завершаться управляемой ошибкой;
- недоступные профили или закрытые группы не должны приводить к аварийному завершению приложения;
- детали ошибки должны сохраняться в истории фонового анализа;
- пользователь должен получать понятное сообщение о причине невозможности анализа.
