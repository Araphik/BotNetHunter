## 1 Введение

Настоящий документ описывает меры обеспечения информационной безопасности, реализованные в системе **BotNetHunter**. Меры сгруппированы по уровням: интерфейсы взаимодействия с системой и среда эксплуатации программного обеспечения.

Система обрабатывает следующие категории данных, требующие защиты:

- учётные данные пользователей (email, хэши паролей),
- сессионные JWT-токены,
- токены доступа к VK API,
- история анализов и их результаты.



## 2 Аутентификация и управление сессиями

### JWT-токены сессии

Аутентификация реализована на основе JSON Web Tokens (JWT) по стандарту RFC 7519.

| Параметр | Значение |
|---|---|
| Алгоритм подписи | HS256 (HMAC-SHA256) |
| Ключ подписи | `SECRET_KEY`  |
| Срок жизни токена | Определяется параметром `ACCESS_TOKEN_EXPIRE_MINUTES` |
| Хранение на клиенте | HTTP-only cookie  |

JWT-токен передаётся в куки с атрибутами `HttpOnly` и `Secure`, что исключает его доступность из JavaScript и защищает от перехвата по незащищённому каналу.

При выходе из системы (`/logout`) куки сбрасывается на стороне сервера.

### Двухфакторная аутентификация (2FA)

Система поддерживает необязательную двухфакторную аутентификацию на основе протокола TOTP (Time-based One-Time Password, RFC 6238), реализованного с помощью библиотеки **pyotp**.

**Регистрация устройства (настройка 2FA):**

1. Пользователь переходит на страницу `/account/2fa/setup`. Сервер генерирует криптографически стойкий Base32-секрет (`pyotp.random_base32()`, 32 символа) и передаёт его клиенту в виде QR-кода (provisioning URI) и текстового ключа.
2. Пользователь сканирует QR-код в приложении-аутентификаторе (Google Authenticator, Authy и совместимые) или вводит ключ вручную.
3. Пользователь подтверждает привязку, отправив текущий 6-значный OTP-код. Сервер верифицирует код (`pyotp.TOTP.verify`, допустимое окно ±1 период, т.е. ±30 секунд), защищая от рассинхрона часов.
4. При успешной проверке секрет сохраняется в базе данных (`users.totp_secret`), флаг `users.is_2fa_enabled` устанавливается в `true`.

**Вход с 2FA:**

При авторизации, если для пользователя включена 2FA, сервер не выдаёт основной JWT-токен сразу. Вместо этого:

| Шаг | Действие |
|---|---|
| 1 | Сервер проверяет email и пароль. При успехе создаётся временный JWT-токен (`step: 2fa_pending`, срок жизни 5 минут), помещаемый в `HttpOnly`-куки `temp_2fa`. |
| 2 | Клиент перенаправляется на страницу `/login/2fa`. |
| 3 | Пользователь вводит OTP-код из приложения. |
| 4 | Сервер извлекает `temp_2fa`, декодирует токен (проверяет подпись и поле `step`), верифицирует OTP. При успехе выдаёт основной JWT и удаляет `temp_2fa`. |

Временный токен подписан тем же `SECRET_KEY`, что и основной JWT, с дополнительным полем `step: 2fa_pending` — подмена основным токеном невозможна.

**Отключение 2FA:**

Пользователь может отключить 2FA через дашборд (`POST /account/2fa/disable`). Поля `totp_secret` и `is_2fa_enabled` сбрасываются в базе данных.

| Параметр | Значение |
|---|---|
| Алгоритм | TOTP (RFC 6238) |
| Библиотека | pyotp ≥ 2.9.0 |
| Длина кода | 6 цифр |
| Период смены | 30 секунд |
| Допустимое окно | ±1 период (±30 с) |
| Хранение секрета | Поле `totp_secret` (VARCHAR 32) в таблице `users` |

### Учётные данные администратора

Учётные данные администратора (`ADMIN_EMAIL`, `ADMIN_PASSWORD`) задаются через переменные окружения и не хранятся в базе данных. 



## 3 Авторизация и разграничение доступа

Система реализует две роли с непересекающимися правами доступа:

| Ресурс | Пользователь | Администратор |
|---|---|---|
| `/dashboard` | + | + |
| `/analyze` | + | + |
| `/history/{id}` | + (только свои записи) | + |
| `/account/change-password` | + | + |
| `/account/delete` | + | - |
| `/admin/*` | - | + |

Доступ к панели администратора `/admin/*` проверяется на уровне каждого защищённого маршрута. Пользователь, не являющийся администратором, получает ответ с редиректом на страницу входа.

Доступ к записям истории ограничен: пользователь может просматривать только собственные записи (`history.user_id == current_user.id`).



## 4 Защита интерфейсов взаимодействия с системой

### 4.1 Защита от CSRF-атак

Все HTML-формы, выполняющие изменение состояния (POST-запросы), защищены механизмом **Double Submit Cookie**:

1. При GET-запросе страницы генерируется случайный `csrf_secret` (32 байта, `secrets.token_hex`), который помещается в `HttpOnly`-куки `csrf_secret` со сроком жизни 1 час.
2. Вычисляется `csrf_token = HMAC-SHA256(SECRET_KEY, csrf_secret)` и передаётся в шаблон как скрытое поле формы `<input type="hidden" name="csrf_token">`.
3. При POST-запросе сервер читает `csrf_secret` из куки, вычисляет ожидаемый токен и сравнивает с полученным из формы с помощью `secrets.compare_digest` — константное время сравнения исключает тайминг-атаки.

Запросы с недействительным или отсутствующим CSRF-токеном отклоняются с ошибкой.

### 4.2 Защита от перебора и чрезмерной нагрузки

Реализован in-memory rate limiter (класс `RateLimiter`) с параметрами:

| Параметр | Значение |
|---|---|
| Максимум запросов | 30 запросов |
| Временное окно | 60 секунд |
| Ключ ограничения | IP-адрес или Bearer-токен |

При превышении порога клиент получает ответ `429 Too Many Requests`. 
Дополнительно реализован дневной лимит анализов на уровне пользователя: при исчерпании лимита запросы к `/analyze` отклоняются до следующего сброса в 00:00.

### 4.3 Защитные HTTP-заголовки

Приложение устанавливает следующие защитные заголовки через middleware для каждого ответа:

| Заголовок | Назначение |
|---|---|
| `Content-Security-Policy` | Ограничивает источники загружаемых ресурсов, предотвращает XSS |
| `X-Content-Type-Options: nosniff` | Запрещает браузерам интерпретировать MIME-тип отличным от объявленного |
| `X-Frame-Options: DENY` | Запрещает встраивание страниц в `<iframe>` — защита от clickjacking |
| `Referrer-Policy` | Ограничивает передачу заголовка `Referer` |
| `Permissions-Policy` | Отключает неиспользуемые браузерные API (геолокация, камера и др.) |
| `Cross-Origin-Opener-Policy` | Изолирует контекст браузера от кросс-доменных окон |
| `Cross-Origin-Resource-Policy` | Ограничивает кросс-доменное использование ресурсов |

### 4.4 Политика CORS

CORS настроен на разрешенные разрешённые источники, которые задаются через переменную окружения `SECURITY_ALLOWED_ORIGINS` списком конкретных URL через запятую. Использование wildcard `*` не допускается.

Пример корректной настройки:
```
SECURITY_ALLOWED_ORIGINS=https://botnethunter.duckdns.org
```

### 4.5 Транспортная безопасность (TLS)

Соединения между клиентом и системой шифруются по протоколу TLS. Конфигурация nginx:

| Параметр | Значение |
|---|---|
| Поддерживаемые протоколы | TLS 1.2, TLS 1.3 |
| Сертификат | Let's Encrypt (автоматическое обновление) |
| Редирект HTTP → HTTPS | Принудительный (301) |

Все запросы по HTTP автоматически перенаправляются на HTTPS. Сессионные куки передаются с атрибутом `Secure`, что исключает их отправку по незащищённому соединению.



## 5 Безопасность среды эксплуатации

### 5.1 Управление секретами и конфигурацией

Все конфиденциальные параметры хранятся в переменных окружения (файл `.env`), который:
- не включён в репозиторий (присутствует в `.gitignore`),
- не копируется в Docker-образ (присутствует в `.dockerignore`).

В репозитории содержится файл `.env.example` с заполнителями (placeholder) вместо реальных значений.

Обязательные секретные параметры:

| Параметр | Назначение |
|---|---|
| `SECRET_KEY` | Ключ подписи JWT-токенов и CSRF-токенов, должен быть длинной случайной строкой |
| `ADMIN_EMAIL` | Email учётной записи администратора |
| `ADMIN_PASSWORD` | Пароль учётной записи администратора |
| `DATABASE_URL` | Строка подключения к PostgreSQL (включает пароль) |
| `POSTGRES_PASSWORD` | Пароль пользователя базы данных |

Отсутствие `SECRET_KEY`, `ADMIN_EMAIL` или `ADMIN_PASSWORD` при запуске является критической ошибкой — приложение не запустится.

### 5.2 Изоляция контейнеров

Система развёртывается в Docker-контейнерах с помощью Docker Compose:

- Приложение (`botnethunter`) и база данных (`postgres`) работают в изолированных контейнерах в рамках одной Docker-сети.
- Порт PostgreSQL (5432) не публикуется во внешнюю сеть — доступен только внутри Docker-сети.
- Внешнему трафику доступны только порты 80 и 443 (nginx), которые проксируют запросы к приложению.

### 5.3 Безопасность базы данных

- Доступ к PostgreSQL осуществляется через ORM-слой SQLAlchemy, что исключает прямые SQL-запросы в коде приложения и снижает риск SQL-инъекций.
- Подключение к базе данных настраивается через `DATABASE_URL`, содержащий учётные данные выделенного пользователя БД (не суперпользователя).
- Данные PostgreSQL хранятся в именованном Docker volume `postgres_data`, изолированном от файловой системы хоста.

### 5.4 Безопасность VK API токенов

- Токены VK API хранятся в базе данных и доступны через интерфейс администратора.
- Клиент (`VKClient`) реализует логику повторных попыток  и задержки между запросами `REQUEST_DELAY`, `FLOOD_WAIT` для соблюдения ограничений VK API и предотвращения автоматической блокировки.



## 6 Безопасность на уровне приложения

### 6.1 Хэширование паролей

Пароли пользователей хранятся в хэшированном виде. Используется алгоритм **Argon2id**.
Сравнение паролей выполняется через `PasswordHasher.verify()`, которая использует константное время сравнения.

### 6.2 Защита от SQL-инъекций

Все запросы к базе данных выполняются через ORM SQLAlchemy с параметризованными запросами. Прямой конкатенации пользовательского ввода со строками SQL в коде приложения не используется.

### 6.3 Дневные лимиты запросов

На уровне пользователя реализованы дневные лимиты анализов:

- Каждый анализ профиля расходует 1 единицу лимита.
- Анализ группы расходует N единиц лимита, где N — количество проанализированных участников.
- При исчерпании лимита новые запросы к `/analyze` отклоняются.
- Лимит обнуляется ежедневно в 00:00.
- Администратор может изменить индивидуальный лимит для каждого пользователя.


### 6.4 Логирование и аудит

Приложение ведёт структурированные логи с уникальными идентификаторами запросов (`request_id`), что обеспечивает возможность отслеживания и аудита. Каждый входящий запрос получает уникальный идентификатор UUID7, который сопровождает запрос через все уровни обработки.



## 7 Мониторинг и метрики (Prometheus)

Приложение экспортирует метрики в формате Prometheus через эндпоинт `/metrics`, предоставляемый библиотекой **prometheus-fastapi-instrumentator** (версия 7.0.0).

### Инструментация HTTP-запросов

Библиотека автоматически собирает следующие метрики для каждого HTTP-маршрута:

| Метрика | Тип | Описание |
|---|---|---|
| `http_requests_total` | Counter | Общее число HTTP-запросов с разбивкой по методу, пути и коду ответа |
| `http_request_duration_seconds` | Histogram | Распределение времени обработки запросов |
| `http_requests_in_progress` | Gauge | Число запросов, обрабатываемых в данный момент |

Группировка по кодам ответа отключена (`should_group_status_codes=False`) — каждый код (200, 404, 429 и т.д.) учитывается отдельно.

### Пользовательские метрики

Дополнительно приложение регистрирует собственный счётчик:

| Метрика | Тип | Метки | Описание |
|---|---|---|---|
| `http_requests_rate_limited_total` | Counter | `path` | Число запросов, отклонённых rate limiter'ом (ответ 429), с разбивкой по пути |

Счётчик инкрементируется в middleware при каждом срабатывании ограничителя частоты запросов.

### Системные метрики приложения

Параллельно с Prometheus-экспортом приложение собирает системные показатели через `psutil` и сохраняет их в таблицу `system_metrics` базы данных (модуль `app/metrics.py`). Эти данные отображаются в панели администратора (`/admin/metrics`) и хранятся 7 дней (автоматическая очистка устаревших записей).

| Метрика | Описание |
|---|---|
| `cpu_percent` | Загрузка CPU (%) |
| `memory_percent` | Использование оперативной памяти (%) |
| `disk_percent` | Использование дискового пространства (%) |
| `network_sent` | Объём переданных данных (байты) |
| `network_recv` | Объём принятых данных (байты) |

### Доступ к эндпоинту `/metrics`

Эндпоинт `/metrics` открыт без аутентификации — это стандартная практика для сбора метрик агентом Prometheus внутри закрытой сети. В производственной конфигурации доступ к нему следует ограничить на уровне nginx (например, разрешить только с адресов сервера мониторинга).



## 8 Рекомендации по безопасной эксплуатации

| # | Рекомендация |
|---|---|
| 1 | Использовать криптографически стойкий `SECRET_KEY` длиной не менее 32 байт (64 символа в hex-представлении), менять при подозрении на компрометацию |
| 2 | Устанавливать надёжный пароль администратора (не менее 16 символов, использовать буквы, цифры и спецсимволы) |
| 3 | Регулярно обновлять зависимости Python (`requirements.txt`) и Docker-образ для получения исправлений безопасности |
| 4 | Не публиковать файл `.env` в репозиторий и не передавать третьим лицам |
| 5 | Ограничить доступ к VK API токенам: хранить только действительные токены и удалять скомпрометированные |
| 6 | Использовать актуальные версии TLS (1.2 и 1.3) и своевременно обновлять SSL-сертификаты |
| 7 | Регулярно проверять системные метрики (`/admin/metrics`) на предмет аномальной нагрузки |
| 8 | Настраивать `SECURITY_ALLOWED_ORIGINS` с перечнем конкретных доверенных доменов, без wildcard `*` |
| 9 | Ограничить сетевой доступ к порту PostgreSQL (5432) только внутренней Docker-сетью — не публиковать во внешнюю сеть |
| 10 | Регулярно делать резервные копии Docker volume `postgres_data` для защиты от потери данных |
| 11 | Рекомендовать пользователям подключить двухфакторную аутентификацию для защиты учётных записей |
| 12 | Ограничить доступ к эндпоинту `/metrics` на уровне nginx — разрешить только с доверенных IP-адресов сервера мониторинга |
